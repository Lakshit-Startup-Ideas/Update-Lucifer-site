Lucifer Lab/Limits

Limits and next steps

What this does not show, and how to help.

Every claim on this site has a limit. They are written down here with the evidence, together with the ways a developer can make the next result harder to dismiss.

LimitsPowerThreatsWhat would change itContribute

What this result does not show

A “no effect” result would have been published too. These are the reasons to read this one as a first look, not proof, each with what would settle it.

1

The baseline is zero by design

The conventions are hidden, so No memory solved 0 of 210 attempts first try. After one retry it reaches 52%. The gain is mostly skipping a failed first try, not solving something that was otherwise unsolvable.

What would settle it Report first-try and after-retry side by side (done), and add tasks where the baseline sits in the middle.

2

Transfer is weak

On similar tasks Lucifer got 67%; on tasks that combine conventions, 17%. It helps most when a new task is close to an old one.

What would settle it A stronger transfer test with new conventions, not only combinations of seen ones.

3

The lesson contains the answer

In these tasks a lesson literally includes the failing test, so the model is using a pasted correct example. Replay at 98% is memorisation. This is real but modest learning.

What would settle it Tasks where the lesson must be abstracted, not copied.

4

One model, 18 scored tasks

One 14B coder model, 12 similar and 6 transfer tasks, 5 seeds, written by the author. The interval is wide for a reason.

What would settle it A second model, and at least about 48 scored tasks (see the power table).

5

Retention is undecided

Because the baseline masters no task, gate 2 has nothing to test and stays inconclusive. The overall verdict is therefore “not all gates passed”.

What would settle it Tasks the baseline already solves often, so forgetting can actually be measured.

6

Some tasks may be unfair

Lucifer never solved shipment_id or ticket_id first try (0 of 5 each), although all seeds passed after a retry. The lessons show ORD, INV and CUS; a model may reasonably guess SHP or TKT. This reading is untested.

What would settle it Read the traces for those tasks; fix or replace any task whose convention a lesson cannot disambiguate.

7

Wrong notes leak a little

In the experience phase, Wrong notes solved 7 of 60 first try against 0 for No memory. Irrelevant lessons can still carry hints early on. In the primary phases it solved 0 of 90.

What would settle it Keep the control; consider a second control with lessons from a different domain.

8

A side run, not merged

An earlier hosted run on another model (one seed) pointed the same way, +0.44, but its other seeds hit a free-tier daily token cap. It is not part of the result.

What would settle it Re-run on a pinned model with all seeds.

Why 18 tasks is thin

The power study, measured on simulated agents.

Measured on simulated agents with a known +20 point effect, 5 seeds, 60 simulated experiments per row. With 18 primary tasks, a real effect of that size is detected only some of the time, so a “no effect” from a set this small would have been weak evidence, and a “yes” is a first look. Even 60 runs leave about ±6 points of noise on these percentages. Smaller true effects need more tasks; that is not measured yet.

What would change the conclusion

What would strengthen the claim

  • The gain holds on a second, different model.
  • It holds on a held-out task family never seen while designing.
  • It holds with 48 or more scored tasks and a tighter interval.
  • Transfer improves with a better-built test.

What would weaken it

  • The gain disappears on a pinned larger model that already fixes conventions.
  • Fixing the unfair tasks removes most of the effect.
  • A harder control, with lessons from another domain, matches Lucifer.
  • The interval crosses zero as tasks are added.

If the next run shows no effect, it gets published the same way. The gates were fixed before the run, and the code and rows are open so anyone can recompute them.

Help wanted

Open source contributions that would make this stronger.

This is a small open project and the most useful help is scrutiny. Concrete ways in, each a self-contained pull request:

Add tasks

New hidden conventions, not renamed copies. Each task needs hidden tests, a reference answer that passes and a naive answer that fails. The existing test test_reference_passes_and_naive_fails checks it. Work in src/lucifer/tasks.py.

Add a model

Run the same experiment on a second model and report it unedited. Backends live in src/lucifer/backends/; runs go through the experiment.yml workflow, no GPU needed.

A held-out family

Design a task family before looking at results, then evaluate it once. This tests generalisation instead of memorisation.

Stronger transfer

Conventions that must be abstracted from examples rather than copied, so memory has to do more than paste a test.

Semantic retrieval

Try embeddings against the TF-IDF baseline in retrieval.py, keeping the same control and metric.

Review the method

Read the method and the tasks and tell me where they are weak. Issues with evidence are as welcome as code.
