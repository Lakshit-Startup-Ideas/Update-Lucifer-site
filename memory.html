Lucifer Lab/Memory

Memory

A notebook you can audit, and try to break.

Lessons are written after failures, chained by hash for tamper detection, and shown to the model later. The mechanism is small on purpose, so that every claim about it can be checked.

What memory is here

Memory here is deliberately plain: a small SQLite table of lessons, each linked to the one before it by a hash. Nothing about the model changes (no weights, no training). The model simply sees a few earlier lessons in its prompt. That makes the mechanism easy to inspect, and it is why the audit can be so strict.

What a lesson holds

id, version, task_id, kind, text,
run_id, seed, parent_hash, hash

kind: 'failure' or 'fix'
version: 1, 2, 3 ... (one per write)

Provenance is built in: every lesson records which task, run and seed produced it.

When one is written

Only in the experience phase, and only for Lucifer and Wrong notes. A failed first try writes a failure lesson. A failure that was fixed on the retry writes a second, fix lesson containing the code that finally passed. In the evaluation phases memory is read-only.

The hash chain

Each lesson's hash covers the hash of the lesson before it. The first lesson links to a genesis value of 64 zeros. This is the exact function from memory.py:

def _hash(parent, version, task_id, kind, text):
    return sha256('|'.join([parent, str(version), task_id, kind, text])).hexdigest()

Change any earlier lesson and its hash changes, so the next lesson's stored parent no longer matches, and so on down the chain. A hash chain makes edits detectable when it is verified. It does not make the memory impossible to change. verify_chain() walks the table from version 1 and returns false at the first mismatch. The tests cover both an edited and a deleted lesson (test_changing_an_old_lesson_is_detected, test_deleting_a_lesson_is_detected).

    Rollback and the audit

    rollback(version) goes back to an earlier version. The later lessons are moved into an archived table, not deleted, together with the version they were rolled back to, so an audit can still see exactly what was undone.

    The audit (audit()) makes three checks, on a copy so the original is never touched:

    1

    Chain

    Every lesson's version, parent and hash recompute correctly from version 1.

    2

    Rollback

    Roll a copy back to the middle: the chain still verifies, the head hash equals the earlier version's hash, and the remaining history is identical to the snapshot taken before.

    3

    Provenance

    Every lesson has a task, a run and a non-negative seed.

    A lesson, written out

    A worked example of a lesson, exactly as it is written. The “failing test” text comes from the real sandbox run on a plain answer:

    A first attempt at 'format_date' failed. The spec said: `format_date(year, month, day)` writes a calendar date as text. this check failed: assert format_date(2026, 3, 5) == '05-Mar-2026'  (AssertionError: )

    Later, on a similar date task, retrieval scores this lesson highly because it shares many words with the new spec (“year”, “month”, “day”, “writes”, “date”, “text”), so it is likely put into the prompt under “Notes from earlier tasks”.     Be clear about what it is

    What this memory does not do. It does not change the model. It does not summarise or generalise: a lesson is the task, the spec and the failing test, so in the convention tasks it literally contains a correct example. The result therefore measures “can the model use a pasted correct example from an earlier task”, a modest but real form of learning. It does not yet show broad skill transfer.
