Lucifer Lab/Method

Method

How the test is built, and why it is fair.

Three conditions, four phases and an exam built so that only learning can pass it. Everything here is taken from the code that ran, including the exact prompts.

QuestionConditionsPhasesThe examOne taskPromptsRetrievalRefereeStatisticsControlsInfrastructure

The question

The one claim: an ordinary open-weight language model, given persistent memory of its own earlier attempts and a feedback signal, solves later, related tasks at a higher rate than the same model without them. A “no” would have been a valid result and would have been published. Everything else (other mechanisms, training, bigger systems) waits until this has a measured answer.

Three ways to prepare

Same model, same exam. The only thing that differs is what the model may remember.

Writes lessonsReads at evaluationWhat it is for
A · No memorynonothingThe honest starting line.
B · Luciferyes, in the experience phasethe 3 most relevant lessonsThe thing being tested.
C · Wrong notesyes, the same waythe 3 least relevant lessonsThe control that matters most. If B beat A but not C, the gain would come from a longer prompt, not from learning.

All three get the same model, the same prompts, the same tasks in the same order within a seed, and the same single retry. Memory is built fresh for every seed and condition, so nothing leaks between runs.

Four phases of a run

Every condition and seed goes through the same four phases with a fresh memory.

PhaseTasksPer condition and seedMemory
1 · Experience12, in a seeded random order12 attemptsWritten to (Lucifer and Wrong notes)
2 · Similar12 new tasks, same convention as an experience task12Read-only
3 · Transfer6 new tasks that combine conventions6Read-only
4 · Replaythe 12 experience tasks again12Read-only

That is 42 task attempts per condition and seed. Over 5 seeds and 3 conditions: 42 × 5 × 3 = 630 recorded attempts. The evaluation order is shuffled once per seed and is the same for all three conditions. Learning happens only in phase 1; in phases 2 to 4 memory is frozen, so nothing can be learned from the exam itself.

The exam

Hidden conventions only feedback can reveal.

Why the conventions are hidden

The first exam used fully specified tasks and strong models scored 96 to 100% with no memory, so it could show nothing. Memory can only help where the model cannot know something up front but can learn it from feedback, like a house format or an exact error message. So each convention task gives a natural spec that leaves the convention out, and only the failing test reveals it.

What “hidden” looks like

The spec for order_id is just “returns the identifier of order number n”. The tests expect 'ORD-00007'. Nothing in the spec says the prefix or the padding. A test (test_convention_tasks_hide_their_convention_from_the_spec) checks that no convention task leaks its convention into the spec.

One task, step by step

What happens every time the model is asked to solve a task. This is the _solve function in experiment.py.

  1. retrieve_memoryLucifer: the top 3 lessons for this task. Wrong notes: the 3 least relevant. No memory: none.
  2. build_promptIf there are lessons, they are placed first under a short header, then the task.
  3. attempt 1The model writes a function (seeded, so the run can be repeated). The sandbox runs the hidden tests in a separate process.
  4. attempt 2, only if attempt 1 failedThe previous code and the failing test's message are appended. Every condition gets exactly this one retry.
  5. memory.write, experience phase onlyA failed first try writes a failure lesson. A failure fixed on the retry also writes a fix lesson.
  6. one row is recordedFirst-try pass, pass after retry, attempts, tokens, time, which lessons were shown. Plus a trace of every step.

How lessons are found

Lucifer picks lessons with plain TF-IDF cosine similarity over words: no neural model, no download. The query is the task's spec plus its function name; each lesson is a document; stop words are dropped. Lessons scoring below 0.08 are not shown, and at most k = 3 are. Ties go to the newer lesson.

The control reverses the ranking: Wrong notes shows the three lessons that match the task least. Random picks were tried first and were often relevant by luck in a small memory, which would have blurred the comparison. Simple word matching was as good as anything tried (word pairs, stemming); semantic retrieval is listed as future work.

    ranked = relevant(query, lessons, k=len(lessons), min_score=-1.0)
    return ranked[::-1][:k]   # the k worst matches

The referee

How an answer is marked.

Model code is run by SandboxExecutor in a separate Python process in a throw-away folder with an empty environment, a 5-second CPU limit and a 1 MB file limit (8 seconds wall time). The candidate is compiled once, then each hidden check is executed in turn. The first failing check is reported to the model as this check failed: <the assert> (<the error>), at most 400 characters. Code is taken from the first fenced block of the reply.

This is hygiene, not a security boundary: model code could still reach the network or files. These tasks are tiny and the run was on a throw-away CI runner. Anything at larger scale needs a container.

Statistics and the three gates

The unit of analysis is the task, not the attempt. For each of the 18 primary tasks the first-try result is averaged over its seeds, giving one number per task and condition. The effect is the mean over tasks of (Lucifer − baseline). The interval comes from a paired bootstrap: resample the 18 task differences with replacement 10,000 times and take the 2.5th and 97.5th percentiles. Resampling tasks (not attempts) is the cautious choice: seeds of the same task are not independent evidence.

The result is +0.50 with a 95% interval of +0.30 to +0.70. You can run this bootstrap in your own browser on the published rows.

Gate 1 · Improvement

Both intervals, (Lucifer − baseline) and (Lucifer − wrong notes), above zero. “Hurts” is declared if the baseline comparison sits entirely below zero.

Gate 2 · Retention

Tasks the baseline solves at least 80% of the time on half of the seeds are picked; Lucifer may lose at most 5 points on them on the other half. Picking and measuring on the same runs fakes “forgetting” (regression to the mean), a bug the dashboard exposed.

Gate 3 · Auditability

The hash chain verifies, rolling back to the middle and forward again reproduces the same history on a copy, and every lesson has provenance (task, run, seed, version).

Where it ran

Nothing heavy runs on a laptop. The experiment is a GitHub Actions workflow (experiment.yml): one parallel job per seed on a CPU runner (4 vCPU, no GPU), each installing a pinned Ollama and pulling the model, then a merge job that joins the seeds, runs the report and the gates, and optionally commits the result files. The run behind this site is workflow run 43163827087; the published files are in commit 1a88d19.
