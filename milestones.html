Version 1 · Does memory help a model solve later tasks?

A frozen model, a memory of its own mistakes, and a controlled test. Closed on 12 November 2026 with a first real result.

The headline result of this version →

  1. 2026-11-11LabDone

    The lab itself

    80 tasks (50 pitfall, 30 hidden-convention) with hidden tests, a sandboxed runner, hash-chained memory with rollback, three conditions, a paired bootstrap and three gates. 125 tests pass.

    • Three conditions on the same model: no memory, Lucifer (relevant lessons) and wrong notes (the least relevant lessons).
    • Every result is computed from raw rows; nothing is typed in by hand.

    Method → Memory →

  2. 2026-11-11CalibrationDone

    A useless first exam, caught early

    Strong models scored 96–100% with no memory, so that exam could never show an effect. Calibration said so before any claim was made.

    • A second, harder task set with hidden conventions was written, then calibrated on three model sizes to pick one that can learn from feedback.

    Journey →

  3. 2026-11-11Scoring bugDone

    A scoring bug found by the dashboard

    The retention check mistook luck for forgetting (regression to the mean). The dashboard exposed it and the gate's selection was fixed.

    • Tasks are now chosen on half the seeds and measured on the other half.

    Journey →

  4. 2026-11-12CI/CDDone

    Everything moved onto CI/CD

    Experiments now run on GitHub Actions: one job per seed, a merge step, gates in the job summary, and published results committed automatically.

  5. 2026-11-12First real resultDone

    First real result · Version 1 closed

    +50 points first-try success over no memory and over wrong notes, interval +30 to +70, on 5 seeds. Published with every caveat.

    • Model qwen2.5-coder:14b, 30 convention tasks (18 scored), 5 seeds, 630 task runs (1,115 model calls counting retries).
    • First try on similar and transfer tasks: Lucifer 50% (similar 67%, transfer 17%), no memory 0%, wrong notes 0%.
    • Gate 1 (improvement) pass, gate 2 (retention) inconclusive because the baseline masters nothing, gate 3 (auditability) pass.
    What this does not show
    • One model, 18 scored tasks, tasks written by the author. This is a first look, not proof.

Version 1.1 · Research log: learning, forgetting, review and tools

A simulation-only research log of eight milestones. Small learners we wrote ourselves, no language model, pre-registered hypotheses, failures kept. The code is open source, in the v1.1/ folder of the Lucifer-BenchMarks repository.

The headline result of this version →

  1. 2026-11-14M1Partly done

    M1 · Read V1 properly and set the rules

    V1 was inspected from its code and tests before anything was built, and a rule was fixed for everything after: write the hypotheses and failure conditions first, commit them, then run.

    • V1 is retrieval into a frozen model: its learning step writes text, no weights change. V1's 125 tests pass on a fresh run.
    • Four weaknesses in V1's memory hash were found and checked by experiment: run id and seed were not covered by the hash, field boundaries could collide, a fully rewritten chain cannot be detected without an outside copy of the head, and the provenance check only tested for non-empty values.
    • A version 2 hash (every field, length-prefixed, anchor check) fixes them, and V1's own formula is kept so V1 data stays verifiable.
    • Every later milestone was pre-registered before its code ran. Changes after seeing results are logged as amendments with the reason.
    What this does not show
    • The literature review is not done: no reference was read, including the Gupta, Jin and Homma book.
    • The map from the original Lucifer ideas to V1.1 is not done: the original architecture and USP documents were not available, so nothing here is derived from them.
    • No formal mathematics beyond the small models in M2 to M5.

    V1 hash findings → M2 pre-registration (first of eight) →

  2. 2026-11-14M2Done

    M2 · Does growing a network help?

    A small recurrent network that can grow or be pruned, compared with a fixed network of the same final size. 20 seeds. The answer is no.

    • Safe growth (new units cannot affect old ones) keeps earlier tasks exactly (error change 8e-17) but ends far worse than a fixed network of equal size: error 0.417 against 0.068.
    • Growth that rewires everything is as capable but wipes the old readouts: earlier-task error went from 0.04 to 195.
    • Growth saved no compute, and pruning by importance was no better than random pruning.
    • The first run was uninformative (every network failed because the task was too hard); it was kept, the fix was logged as an amendment, and the task difficulty was set using fixed networks only.

    Safe growth keeps old tasksPasschange 8e-17
    Rewiring growth forgetsPass0.04 → 195
    Safe growth matches a fixed net of equal sizeFail0.417 vs 0.068
    Growth saves computeFailsame size at the end
    Growth beats the small fixed netPass0.417 vs 0.598
    Importance pruning beats randomFailno difference
    What this does not show
    • A toy simulation. It does not say dynamic networks cannot work, only that this design gave no benefit and was not adopted.

  3. 2026-11-14M3Done

    M3 · A hybrid executive: what each part is worth

    Four separable mechanisms (a protected goal slot, a failure monitor, learned reliability estimates, cost-aware choice) in a designed world, each removed in turn.

    • In the combined world the executive completed 0.79 more episodes than a plain router.
    • Each part helped only where its failure mode exists: protected goals under interruptions (+0.77), the monitor under failures (+0.24), learned estimates after drift (+0.28).
    • Overhead is real: 4 to 6 control steps per episode; in a world where nothing can fail the executive adds 4.2 steps and 0.21 extra cost for zero gain.
    • Two of three registered checks failed: my 'benign' world still had 3% failures, and cost-aware choice saved 0.40 cost units against the 0.5 I had registered.
    CheckVerdictEvidence
    Executive helps where neededPass+0.794
    No gain in a benign worldFail+0.104 (3% failures remained)
    Each part helps only where neededFail2 of 8 sub-checks missed
    What this does not show
    • The world and the executive were both written by us, so effect sizes follow our parameters. This does not show planning or reasoning.

  4. 2026-11-14M4Done

    M4 · Learning from experience, and forgetting

    Retrieval, parameter adaptation and two protections against forgetting on one stream of 12 contexts, 30 seeds. The log of experience is kept separate from learning.

    • Forgetting is real: the plain learner forgot 0.159 of what it had learned.
    • A consolidation anchor (a pull toward the previous weights) cut forgetting from 0.159 to 0.021 with no raw experience stored, at a cost of 0.014 accuracy.
    • Replay of a 100-example buffer made forgetting slightly worse; it needed 300 to 960 stored examples to help, which conflicts with keeping raw experience local.
    • Logging an experience does not change the model; replaying the learning log reproduces training exactly; deleting a record does not unlearn it, rebuilding from a checkpoint without it does.
    • The registered check that experience speeds up learning new contexts failed on its first-10-examples measure (see M8 for a different measure).
    CheckVerdictEvidence
    Parameters adapt beyond retrievalFailno first-10 speed-up
    Replay (100) protectsFail−0.023
    Anchor protects, no stored experiencePass0.159 → 0.021
    Logging ≠ learning; unlearning needs retrainingPass9 tests
    What this does not show
    • A small simulated learner. Nothing about language models.

  5. 2026-11-14M5Done

    M5 · A parent and independent children

    An in-process parent coordinator and children that each keep their own raw data. The parent receives only metadata: hashes, names, numbers.

    • Registration, message authentication, replay protection, a strict allow-list of fields, anchored audits of each child's history, and checkpoint integrity: 31 tests, 6 of 6 deliberate breakages caught.
    • When two tenants' rules conflict, a model per tenant beat one shared model by 0.147; when the rules agree, sharing gained only 0.009 (the registered 0.02 was missed).
    • A written threat model lists what is not covered: real key management, transport security, covert channels and inference from parameters.
    CheckVerdictEvidence
    Nine protocol propertiesPass31 tests
    Personal beats shared when rules conflictPass+0.147
    Sharing helps when rules agreeFail+0.009 < 0.02
    What this does not show
    • A prototype in one process. It is not evidence that a deployed system is secure.

  6. 2026-11-14M6Done

    M6 · Reviewing knowledge before it is shared

    A package is the decision rule one child learned for one context. Review combines metadata checks with evaluation by other children on their own private data; promotions are versioned and reversible.

    • Valid metadata proves nothing about benefit: all 180 poisoned packages passed the metadata checks. The full review accepted none of them (0 of 180, which bounds the true rate only to about 1.7%).
    • It also blocked 28% of honest, useful packages (72% accepted; the registered target was 80%), and blocked all tenant-specific ones.
    • A poor tenant gained 0.109 accuracy on the contexts where knowledge agreed; blindly adopting everything lost 0.10 to 0.15.
    • Promotion and rollback are entries on a hash chain; rolling back restores the exact earlier state and keeps the archived entries.
    CheckVerdictEvidence
    Review blocks poison; metadata alone failsPass0/180 vs 180/180
    Review lets agreeing knowledge throughFail72% < 80%
    Tenant-specific knowledge not sharedPass0/180
    Transfer to a poor tenantPass+0.109
    Versioning, rollback, tamper evidencePass23 tests
    What this does not show
    • Not tested: an attacker who optimises against the reviewers' data, colluding reviewers, and whether a shared rule vector leaks information about the data it came from.

  7. 2026-11-14M7Done

    M7 · Own tool engine, with MCP and A2A on top

    A tool engine that denies by default, validates input and output, rate-limits, times out, requires one-time approvals for external effects and audits every call without storing raw data.

    • The MCP adapter was checked against the current specification first: the newest revision (2026-07-28) removed the old handshake. The adapter speaks the earlier handshake era and was tested against the official Python client in two modes, which listed, called and received tool errors correctly. The newest revision is not supported and not claimed.
    • A runtime with retries, back-off and crash recovery that never repeats finished work; an in-process model of the agent-to-agent task lifecycle; a browser policy layer that refuses look-alike addresses, never fills passwords or card numbers, and needs a one-time approval to submit.
    • 193 tests; 21 of 22 deliberate breakages caught (the 22nd changes nothing, by construction).

  8. 2026-11-14M8Done

    M8 · Everything rerun, two gaps closed, one report

    Two hypotheses nobody had tested (maturation and unseen task families) were tested, and every experiment was rerun from scratch to confirm the verdicts.

    • Maturation (less plasticity, more consolidation with age) halved forgetting but lost 0.027 accuracy, outside the registered tolerance: failed.
    • Experience helped on new contexts of the same family (+0.065) but was not shown safe on a different family (−0.022, interval touching zero): failed as registered.
    • Everything reran in 67 seconds: all 23 verdict flags identical and no numeric difference. Measured overhead: the tool engine adds about 176 microseconds per call; an audit entry costs 2.65 microseconds.
    • Scoreboard: 21 registered threshold hypotheses, 10 passed and 11 failed, with no threshold ever moved; every property check passed.
